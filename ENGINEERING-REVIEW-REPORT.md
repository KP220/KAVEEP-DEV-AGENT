# Engineering Risks

Architecture Duplication Risk

Creating a new KAVEEP-DEV-AGENT-ARCHITECTURE-BLUEPRINT.md would duplicate ARCHITECTURE.md. This was avoided.

Runtime Drift Risk

Defining engines too concretely could imply runtime implementation. This was avoided by keeping changes architectural and documentary.

Provider Lock-In Risk

The prior model architecture was model-agnostic but did not define KAVEEP Brain v1. This was addressed by documenting Cloud Brain, Local Brain, and the LLM Adapter boundary.

Identity Ambiguity Risk

Some existing language described the repository as an AI platform. This was clarified by defining KAVEEP-DEV-AGENT as a Thai-first AI Software Engineering Organization.

Specification Gap Risk

Several future capability specifications remain missing. This is acceptable for the current milestone but should be addressed in later engineering work.

Referenced Standard Gap Risk

ENGINEERING-CAPABILITY-MODEL.md references ENGINEERING-ENGINE-STANDARD.md and ENGINEERING-TASK-STANDARD.md, but those files are not present. This should be resolved in a future standards milestone.

# Schema Findings

schemas/dev-agent-report.schema.json composes the canonical KAVEEP-CORE report envelope through JSON Schema allOf.

The referenced CORE report envelope path exists:

- ../../KAVEEP-CORE/schemas/report-envelope.schema.json

DEV-AGENT-specific report content is stored under:

- metadata.devAgentPayload

The schema does not locally redefine the CORE report envelope fields. It constrains the producing module to KAVEEP-DEV-AGENT and adds DEV-AGENT-specific payload under CORE metadata.

POLICY-owned records are represented through references in policyEvaluationRefs, riskAssessmentRefs, and approvalRequestRefs.

SIA analytical payloads are not embedded. SIA reports are represented through siaReportRefs.

RO repository-analysis payloads are not embedded. RO reports are represented through roReportRefs.

COMMAND-CENTER mission, workflow, task, agent, session, event, approval-routing, and audit records are not embedded. DEV-AGENT stores missionId, workflowId, and taskId only as foreign identifiers and references Command Center reports through commandCenterReportRefs.

Foreign-domain data is represented through lightweight external report references, schema references, evidence references, audit references, and IDs.

Dependencies on sibling repositories are optional at the DEV-AGENT payload level except where a report example intentionally demonstrates an integration reference.

Schema ownership is semantically aligned with repository sovereignty.

# SPEC-008 Secure Sandbox Foundation

## Engineering Summary

Implemented exactly one controlled runtime milestone: Secure Sandbox Foundation. It prepares bounded isolated copies in unique operating-system temporary directories while preserving the approved source repository unchanged. It introduces no engineering editor, process runner, shell, Git, network, dependency installation, deployment, autonomous execution, or external write-back.

## Capability Implemented

Added canonical Sandbox Request, Manifest, and Result contracts; narrow sandbox-preparation gate evaluation; Secure Sandbox Manager; source snapshot; sandbox-only change detector; explicit verified cleanup; examples; CLIs; focused tests; invalid-contract modes; package scripts; and canonical documentation.

## Repository Discovery and SPEC Decision

SPEC-006 and SPEC-007 already owned read-only tool orchestration and gate evaluation. SPEC-008 was the next capability number. Repository Intelligence already contained canonical containment, approved-root, ignored-name, sensitive-path, normalization, and no-follow behavior. Its pure classifiers were exported and reused rather than duplicated. Existing validation helpers and CORE evidence/audit references were reused.

## Sandbox Lifecycle and Isolation Design

Lifecycle is explicit request -> exact `allow_sandbox_preparation` Gate Result -> canonical source validation -> unique OS-temporary root -> bounded snapshot and copy -> manifest/result -> sandbox-only change detection -> explicit cleanup. The temporary root uses `mkdtemp` and an unpredictable suffix, cannot be caller-selected, cannot equal or reside in the source, and records manager identity metadata. Ready state means isolation preparation only.

## Source-Root Protection and Copy Policy

Missing, non-directory, drive-root, system-root, and entire-home scope are rejected. Selected-context mode copies only selected permitted paths; bounded-repository mode traverses only the canonical source root. Traversal escape is denied. `.git`, dependencies, generated output, caches, builds, virtual environments, and temporary paths are excluded and recorded without claiming irrelevance.

## Resource Limits

Schema and runtime enforce maximum file count, directory count, total bytes, single-file bytes, depth, path length, and lifetime. Limit effects stop affected copying, remain explicit in warnings, and yield `ready_with_warnings` for a usable bounded partial workspace.

## Sensitive Artifact and Link Protection

Environment, credential, secret, token, password, private-key, SSH-key, and private-certificate paths are excluded without content reads, hashes, or copies. Symbolic links, junctions where detectable, and unsupported link-like entries are never followed; exclusions and honest limitations are recorded.

## Source Snapshot and Change Detection

The pre-copy permitted-source snapshot records normalized relative paths, type, size, modification timestamp, and SHA-256 for permitted files. It does not hash secrets and is not a Git replacement. Change detection reports added, modified, deleted, unchanged, excluded, and unverified sandbox entries plus bound effects, and never writes to the source.

## Cleanup Safety

Cleanup accepts only an exact `sandbox-manifest.json`, then verifies canonical OS-temp containment, manager directory prefix, sandbox identity, source identity, and the internal unpredictable marker. Source paths, arbitrary paths, unknown sandboxes, and broad temporary cleanup are rejected. Preparation failure removes its own partial workspace; tests clean only their verified workspaces.

## Execution Gate, Tool Orchestrator, and Future Boundaries

Execution Gate now owns the narrow `allow_sandbox_preparation` decision for one exact Sandbox Request, request, and plan with evidence. This permits bounded isolated copying only. Tool Orchestrator is not automatically connected. No planning or LLM trigger exists. Future File Editor and Process Runner capabilities require separate milestones and must be sandbox-restricted; sandbox readiness grants no source write-back.
